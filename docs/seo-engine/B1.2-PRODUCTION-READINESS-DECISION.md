### Activation measurement

The activation definition used by the production aggregate query and synthetic fixture is:

1. A registered profile exists.
2. Onboarding has a non-null completion timestamp at or after registration.
3. At least one persisted non-void invoice or persisted expense has `created_at >= onboarding_progress.completed_at`.
4. A returning activated user has qualifying activity on at least two distinct UTC dates after onboarding.

The fixture includes users with no completed onboarding, void invoices, only pre-onboarding activity, and one pre-onboarding action day plus one post-onboarding action day. The latter user activates but is not counted as returning. Expected fixture totals are 8 registered, 7 completed onboardings, 3 activated, and 1 returning activated.

The production query was executed as SELECT only against the live schema. The point-in-time aggregate returned 36 registered profiles, 2 completed onboardings, 1 activated user, and 1 returning activated user. For the last 30 days it returned 5 registrations, 0 onboardings, and 0 activations. Expenses have no status/reversal column, so a persisted expense is treated as qualifying; this is an explicit limitation.

### Scheduling, recovery, and monitoring

- The three workflows expose daily cron schedules and `workflow_dispatch` for manual recovery. Their configured cron times are 00:15, 01:45, and 03:15 UTC.
- Scheduler 2 fails closed unless Scheduler 1 has a successful run for the same UTC day. Scheduler 3 fails non-zero when required persistence is unavailable and uploads its report even on failure.
- GitHub Actions logs and artifacts provide current diagnostics. There is no verified external alerting, on-call ownership, delivery SLA, or continuous 24/7 service guarantee. GitHub scheduled workflows are best-effort and can be delayed.
- Main-branch evidence before this PR: Scheduler 1 failed on the Search Appearance dimension-combination API error ([#44693491897](https://github.com/ttheodathe/finflow-stabilize-grow/actions/runs/44693491897), [manual recovery #44740152487](https://github.com/ttheodathe/finflow-stabilize-grow/actions/runs/44740152487)); Scheduler 2 correctly stopped because Scheduler 1 had not succeeded that day ([#44708659394](https://github.com/ttheodathe/finflow-stabilize-grow/actions/runs/44708659394)); Scheduler 3 previously exited successfully with `persistenceStatus=NOT_CONFIGURED` ([#44730301271](https://github.com/ttheodathe/finflow-stabilize-grow/actions/runs/44730301271)). The PR fixes the GSC request dimensions and Scheduler 3 fail-closed behavior. These main-branch workflows remain unchanged until the PR is merged.

## Production blockers

1. **Production persistence design:** establish a dedicated least-privilege production read-only aggregation mechanism. Do not reuse the acceptance service-role key or point production workflows at the acceptance project.
2. **Activation automation:** the production aggregate query has been manually validated with SELECT only. It is not yet scheduled or persisted as a production activation snapshot.
3. **Performance feedback:** either implement and validate the Scheduler 2 → Scheduler 3 page-level outcome link, or explicitly defer content-impact attribution from the first production milestone.
4. **Operations:** define alerting, run-failure notification, recovery ownership, retry policy, artifact retention, and expected completion windows.
5. **Production migration plan:** review production schema, grants, RLS, migration ordering, rollback strategy, and deployment permissions separately. The acceptance migration ledger must not be copied blindly to production.
6. **Human approval:** preserve the current human-review gate. Do not auto-approve, publish, or update live content.

## Final disposition

- PR #120 is merged; its merge does not change this document's **NOT READY FOR PRODUCTION** decision.
- Keep publishing and production content updates disabled until the listed production blockers are closed with evidence.
- Do not run production migrations or production writes as part of this milestone.
- The acceptance pipeline is verified; production readiness is not. Reassess only after every blocker above has evidence-backed closure.
